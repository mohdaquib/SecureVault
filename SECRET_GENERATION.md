# Secret generation

Application-generated secret bytes come from the internal `SecretGenerator` in
`:securevault-crypto`. Its production instance uses `java.security.SecureRandom`
without a caller-supplied seed. Database passphrases are 32 bytes (256 bits).
Each call allocates and fills a new buffer. Invalid lengths fail before asking
for randomness; source failures propagate without a weaker fallback.

Android Keystore continues to generate AES-256 keys using its `KeyGenerator`.
Keep those keys inside Keystore; do not replace them with app-generated raw keys.
AES-GCM nonces/IVs are generated by the cryptographic provider when encryption is
initialized. Store the returned IV with the ciphertext and use it for decryption;
do not generate it with a counter, timestamp, or general-purpose random source.
There are currently no salt-generation paths. Any future app-generated salts or
secret bytes should use `SecretGenerator` with lengths required by their algorithm.
Protocol-specific nonce requirements must still be followed.

The passphrase store calls the generator only when creating a new vault secret.
Reopening existing storage decrypts and returns its saved secret, including legacy
demo storage. This change does not rotate keys or change the stored format.

Tests use an injected deterministic SecureRandom subclass, confined to test code.
They check the exact requested length, invocation count, fresh buffer allocation,
invalid input, failure propagation, and reuse of an existing passphrase. They do
not test distributions or depend on randomly generated outputs being different.
The production API does not expose this test injection point.

Tests added for this change have not been executed because building and compiling
were explicitly excluded from the task. Run `:securevault-crypto:testDebugUnitTest`
when build execution is permitted.
